# 项目会话需求分流

仅分析当前用户输入和确定归属所需的最小上下文，不遍历历史聊天。
这是一项可发现的技能，不是全局输入监听器。安装技能也不证明每次桌面输入
都会触发；只有已验证的宿主事件入口才能声称自动覆盖。连接不可用时说明缺口，
不要修改全局配置、安装 hooks 或启动 daemon。

使用同级 `../manage-delivery/scripts/bridge.py`：

```bash
python3 "$BRIDGE" catalog
python3 "$BRIDGE" list
python3 "$BRIDGE" intake --json '{"event_id":"HOST_INPUT_ID","thread_id":"CURRENT_THREAD_UUID","project_id":"PROJECT_ID","intent":"create","reason":"明确请求增加导出能力","patch":{"title":"支持导出","description":"脱敏需求","acceptance":"验收标准"}}'
```

由模型按语义选择，不按关键词规则猜测：

- `ignore`：天气、闲聊、与项目无关的问题；不修改需求，即使出现在需求聊天框。
- `create`：明确的新能力或缺陷修复；先确认项目、查重，不把每次输入都新建需求。
- `update`：对已确认需求的范围、描述或验收标准做明确变更。
- `archive`：明确取消需求，只提归档，不物理删除、不取消正在执行的任务。
- `clarify`：需求归属、引用对象或变更意图不明确；向用户问最小必要问题。

技术问答和进展讨论不当然是需求变更。比如“今天天气如何”应忽略，
“给天气项目增加当天预报”则可能是新增；“这个按钮为什么不工作”
需根据上下文区分问题咨询与修复请求。提取实际要求，不扩写用户没有要求的范围。

`event_id`使用宿主稳定输入编号，不用随机数或时间戳代替，重放时保持全部分类内容一致。
拿不到事件/会话/项目准确编号时不要提交，报告需要的入口。不得根据标题猜会话归属。
`update`/`archive`另传 `item_id`、当前 `version`，必须是该项目内已人工绑定当前会话的
本地需求；外部导入记录仍由原工具更新。`patch`只含 title/description/acceptance/kind，
不含进度、审批、执行命令。服务器不运行模型，分类依据是代理声明而非独立认证。

仅发送短脱敏摘要与分类依据，不保存原始聊天、令牌、工单或生产数据。
标题只写用户可识别的业务对象和改动，建议 8 至 24 字，如“导出按钮修复”；
不要把验收、实现细节、授权限制或记录来源塞进标题，它们属于描述或验收标准。
不把多个独立需求统一改名成一个宏大项目目标；同一目标的子项仍须可区分。
`ignore`不写需求；其余变更在 Web 收件箱经人工采纳才写入，待澄清不能直接采纳。
新的需求建议保留来源会话编号，采纳后仍须人在详情中确认关联，不自动读取会话或发送消息。
审批与生产权限沿用原边界，自定义流程节点不授权执行生产操作。
